## Round 1 · 2026-11-24 · verdict: APPROVE

`pnpm verify`: ✅ (exit 0, run by the main session); `pnpm e2e` 42 of 42 passed (reported by FE-02)

AC1–AC12 are built as written, and each one has a real test titled `S02.2 AC<n>`. The AC9 matrix (anonymous 401; pending, rejected and contributor 403, each against all three endpoints, with the target row unchanged) passes over HTTP. `@Admin()` sits on the controller class, and the global `AccessGuard` requires `APPROVED` + `ADMIN`. Approve and reject are one conditional `UPDATE … WHERE id AND status = 'PENDING' RETURNING`. The follow-up lookup only chooses between 404 and 409, and a test proves that two calls at once give one 200 and one 409. Bootstrap decides and writes in one transaction. The list is one query ordered by `created_at, id`. Responses go through `toAdminUserResponse`, which has no hash field. The web uses the shared schemas through `client.ts`, and every state in "UI states" has a component test, including the 401 and 403 re-gating. No new schema, so the migration still matches the entities.

Developer points:
- **1, no index on `users.role` / `users.status`:** see F1. With two or three values on about 100 rows, PostgreSQL would scan the table anyway, so an index would add nothing. The gap is that the design made an exception to a named rule without writing it down. Documentation fix, no code.
- **2, the date in the browser's time zone:** correct, no finding. The admins are in the lab, so their local calendar date is the useful one. `<time dateTime>` keeps the exact UTC instant. The fixtures sit at midday UTC (`apps/web/src/test/msw.ts:82-95`), so the component test gives the same result in every lab time zone.
- **3, FE-02 specs never seen failing:** acceptable, no finding. A browser journey written after its page exists cannot be red first. These specs would fail if a step broke: each assertion waits on something concrete (the row filtered by its unique email, the `status` text, the heading after reload, the banner name before "Sign-ups" is checked as hidden), and none can pass while `me` is still loading. AC4–AC11 were test-first in FE-01's component tests.
- **FE-02's change to `e2e/tests/accounts.spec.ts` (S02.1 F3):** approved. `:143-155` now signs up a real person, has the setup admin approve them in their own context (`e2e/helpers/accounts.ts:93-105`), and checks `/contribute` with the person's own cookie. No `page.route` fake is left in `e2e/`. The other S02.1 tests only moved to the shared helpers, and their assertions are unchanged.

- [ ] F1 [minor][be] `apps/api/src/db/migrations/1795521437455-CreateUsersAndSessions.ts:8`: `users.role` (`users.service.ts:88`) and `users.status` (`users.service.ts:113,130`) are used in `WHERE` but have no index. `apps/api/CLAUDE.md` "Queries" says every such column gets one. Both tickets said "Schema change: no", and design.md does not mention an exception, so this is a gap in the design rather than in the code. S02.3's `WHERE role = 'ADMIN' FOR UPDATE` will add a third use. Fix: the architect adds a line under design.md "Data" saying low-cardinality `role` and `status` on a table of about 100 rows are deliberately not indexed, with a "Changes" line. No migration.
- [ ] F2 [minor][be] `.env.example:11-13`: the three `BOOTSTRAP_ADMIN_*` lines are not commented out, unlike `WEB_DIST_DIR` and `COOKIE_SECURE`. `change-this-password` passes the sign-up rule, so a server set up by copying this file starts with an admin whose password is public. Fix: comment out the three lines and keep the explanation. In `.env`, a developer then sets their own values.
- [ ] F3 [minor][be] `apps/api/src/modules/users/bootstrap-admin.service.ts:49-52`: when no admin exists, whoever signs up first with the address that will later go into `BOOTSTRAP_ADMIN_EMAIL` becomes admin on the next start, using their own password. This works even for a `REJECTED` account. There is no email verification, so that person need not own the address. This follows design.md open question 2 and AC1 as written, so it is not a defect. But it is a privilege-escalation path that is not listed under "Risks". Fix: record it under design.md "Risks", with the mitigation "set the `BOOTSTRAP_ADMIN_*` settings before the first public start". Alternatively, raise a change so that promotion only happens when `BOOTSTRAP_ADMIN_PASSWORD` verifies against the existing hash, and start-up fails otherwise.
- [ ] F4 [minor][fe] `apps/web/src/pages/admin-sign-ups/SignUpRow.tsx:53-56`: "Yes, reject" unmounts itself before the request is sent. If the reject then fails (500 or a network error), keyboard focus is left on `<body>`, and a keyboard user has to tab again from the top of the page to reach the row. The same happens after "Approve", because the focused button is disabled while sending. Fix: after a failed action, return focus to the row's "Reject" or "Approve" button, with a component test.
