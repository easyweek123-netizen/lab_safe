## Round 1 · 2026-11-24 · verdict: APPROVE

`pnpm verify`: ✅ (exit 0, run by the main session: shared 71, API unit 133, web 117, integration 169, docs-check OK); `pnpm e2e` 52 of 52 passed (reported by FE-02)

AC1–AC12 are built as written, and each one has a real test titled `S02.3 AC<n>`. `PUT :id/role` joins `AdminUsersController`, which has `@Admin()` on the class, so the route refuses by default. The AC9 matrix passes over HTTP: an anonymous visitor gets 401, and pending, rejected and approved-contributor callers get 403, each against both endpoints, with the target, the admin and the caller rows unchanged. Self-promotion and a foreign `Origin` are refused too. `changeRole` follows invariant I7 and design "Flows": it runs as one `dataSource.transaction`, takes the admin rows `FOR UPDATE` in id order before it counts, then locks the target row, and every query goes through `manager`. The checks run in this order: 404, then `USER_NOT_APPROVED`, then "role already held" (200, no write, `updated_at` unchanged), then `LAST_ADMIN`. The AC6 test really is deterministic: a separate `pg` connection holds the lock, the test waits on `pg_blocking_pids`, and the ticket notes say it failed with the lock removed. The approved list is one query ordered by name, email, id. Responses go through `toAdminUserResponse`, and the log line has only the id and the role. On the web, `client.ts` and the shared schemas are used. Each row owns its mutation, so only that row's button is disabled. A self-demotion, a 401 or a 403 invalidates `me`, so the gate re-decides at the same URL. Every "UI states" cell has a component test. No schema change, so the migration still matches the entities.

Points for judgement:
- **1, the two S02.2 cases removed by BE-01:** this is a contract change, not a weakened test. S02.2's own contract (`S02.2-approve-signups/story.md:36`) says "S02.3 adds `APPROVED`". S02.3's contract adds it, and new tests accept it (`packages/shared/src/schemas/admin-users.test.ts` "S02.3 AC1 accepts status APPROVED"; `apps/api/test/admin-roles.int.test.ts:105`). Every other refused value (missing, `REJECTED`, lower case, repeated) is still refused in both files, and S02.3 repeats those cases against `?status=` (`admin-roles.int.test.ts:163-176`). Only the wording of S02.2 AC8 is now out of date: see F2.
- **2, design.md "Endpoints":** no finding needed. The line already reads `AdminUsersQuery {status: PENDING (S02.2) | APPROVED (S02.3)}`, and "APPROVED lists by name, then email" is in the paragraph under the table. BE-01's note that it still says only "PENDING" is itself out of date.
- **3, FE-02 passed on its first run:** acceptable, no finding, for the same reason as S02.2. Every step waits on something concrete: the row filtered by its unique email, the `status` text, "Role: Admin" in the row, the banner links after `page.reload()` in the person's own context, the "No access" heading, then `/contribute`. The spec would fail if promotion or demotion did not take effect on the next page load. The `finally` puts the shared database back to one admin.
- **S02.2 F1 (no index on `users.role` / `users.status`)** is still open. `changeRole`'s `WHERE role = 'ADMIN' FOR UPDATE` (`users.service.ts:171-177`) is the third use that S02.2 F1 predicted. No new finding: the fix is the same line in design.md "Data".

- [ ] F1 [minor][be] `apps/api/src/modules/users/users.service.ts:171-177`: under READ COMMITTED, the locking `SELECT … WHERE role = 'ADMIN' FOR UPDATE` only sees rows that were admins when the statement started. Take the case where admin A promotes C while A, in another tab, demotes A at the same moment. The demotion waits on A's row lock. When it gets the lock, it still sees `{A}` and answers 409 `LAST_ADMIN`, although C is an admin by then. This only fails on the safe side: no admin is ever lost, and a retry succeeds. Fix: either record it under design.md "Risks" as an accepted false refusal under a concurrent promotion, or re-read the admin ids with a plain `SELECT` through `manager` once the locks are held (a new statement sees the committed promotion), and add a test.
- [ ] F2 [minor][docs] `docs/epics/E02-accounts-access/S02.2-approve-signups/story.md:26,45`: AC8 still says "a `status` other than `PENDING` gives 400 `VALIDATION_FAILED`", and the endpoint row still reads `?status=PENDING` only. Since S02.3, `APPROVED` is valid. Fix: at `/complete-epic`, add "(S02.3 also allows `APPROVED`)" to AC8 and add a "Changes" line to S02.2's story.
