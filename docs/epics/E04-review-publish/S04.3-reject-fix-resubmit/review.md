AC1 to AC11 are built as written, and each has a real test titled `S04.3 AC<n>`. The contract is `RejectSubmissionRequest` (trimmed, 1–1,000, the two texts of the story) and `reviewNote: string | null` in `Submission` and `SubmissionSummary`. The API parses the reject body with it through `ZodValidationPipe`, and the web checks the note with the same schema before sending.

**Rejecting (AC1–AC3).** `@Admin()` on `AdminReviewController` covers the new route, and `RequestOriginGuard` covers the POST. `ReviewService.reject` is one `UPDATE … WHERE id AND status = 'PENDING' RETURNING id`. It sets the status, the trimmed note, the reviewer and the date. No row means 404 for an unknown id, otherwise 409 `ALREADY_REVIEWED`. The log line has ids only. The tests check the stored row (note, reviewer, date, `submitted_at` kept), line breaks, the queue and preview afterwards, that nothing is published and that no other page changes. They cover six missing-note bodies, too long and exactly 1,000, and the full refusal matrix (anonymous 401; pending, rejected, contributor and author 403, with no page name in the body). They also cover approved, already-rejected, malformed and unknown ids and a foreign `Origin`, and compare the stored tables each time.

**Fix and resubmit (AC4–AC9).** `noteOf` returns the note only for `REJECTED`, in `listMine`'s one query and in `loadSubmission`. `PublishedSafetyPage` has no note, which is tested on the public body. `update` keeps E03's row lock on `id AND submitted_by = me`, runs the room and photo checks first, and then, in the same `UPDATE`, sets `PENDING`, `submitted_at` now, the three review columns null and `version + 1`. A refused body leaves the page rejected with its note, and the tests compare all four tables. AC8's matrix is complete: reads 200 for the author and an admin and 404 for everyone else with the unknown-id body; `PUT` 404 for an admin and everyone else, also with their own photo; the photo. AC9 checks the replaced photo after approval: 404 to anonymous and to another contributor, 200 to its owner.

**Web (AC1–AC7, AC10).** `DecisionPanel` places the note and "Reject" under "Approve", which is tested by DOM position. A refused note shows next to the field with focus and sends nothing. A server `fields: note` is shown the same way and not as an alert, and there is one alert at a time across both decisions. "My submissions" shows "Admin's note: …" in `whitespace-pre-wrap` only for a rejected row. `EditSafetyPagePage` picks edit or fix when the form is first shown. It shows `ReviewNote` (h2, before the form), "Resubmit for review" / "Resubmitting…" and the confirmation for the mode. Every AC10 state is tested, including five kinds of background refresh. **e2e** runs the whole C2–C8 journey in both projects, with the anonymous checks while pending, rejected and resubmitted, and after approval.

Developer points:
- **1, BE-01 conditional `UPDATE` instead of `FOR UPDATE`; fixtures:** accepted. The ticket asked for the conditional update. It gives the same "reviewed once" guarantee in one statement. Against an author's `PUT`, which holds the row lock, the `UPDATE` waits and then checks `status = 'PENDING'` again (READ COMMITTED), so it is safe there too. The two-admins test proves exactly one 200 and that the winner's note is stored. The web and API fixture changes only add `reviewNote: null` (and `slug: null`). No assertion was removed, and the two expected bodies are still exact. The design's wording is F2.
- **2, BE-02 changed `S03.2 AC5` test:** not a weakened test. S03.2 AC5 is "Given a **pending** submission". The rejected-row case was an extra E03 test of a rule that S04.3 AC6 now replaces for the author only. The new version keeps the 404 and the unchanged stored rows for more callers than before (anonymous, pending, rejected, another contributor, admin). It also asserts the author's new 200 `PENDING` with no note, which BE-02 foresaw in its notes and S04.2 BE-03 recorded.
- **3, FE-02 mode fixed at first show:** accepted. It is E03-D7 and AC10's "a background refresh never resets the form", and `formShown` is UI state set during render, not a copy of server data. Choosing the confirmation by mode is right, because the response is `PENDING` for both a save and a resubmission. The note disappearing in fix mode after a refresh answers pending or approved is acceptable: the server no longer has it. The opposite direction is F1.
- **4, FE-03 reused JPEG, timestamps:** accepted. The server re-encodes every upload into a new row, and the spec asserts that the two ids differ, so the replaced photo is really a different photo. Comparing `<time datetime>` is the only way to tell two dates on the same day apart. "After the earlier pages" is safe because Playwright runs with `workers: 1`. Passing on the first run is fine for a journey check over behaviour already covered at lower levels. Its assertions are exact and could fail.

- [ ] F1 [minor][fe] `apps/web/src/pages/edit-safety-page/EditSafetyPagePage.tsx:115`: the admin's note shows only in fix mode. A background refresh then brings `REJECTED` with the note, but the note stays hidden ("S04.3 AC10 keeps the pending edit form unchanged …" asserts exactly this). "Save changes" then resubmits on the server and clears the note. The admin's feedback is lost without the author ever seeing it, and the confirmation says the changes were saved.
