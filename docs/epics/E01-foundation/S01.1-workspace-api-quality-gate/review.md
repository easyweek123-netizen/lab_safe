- [ ] F1 [minor][be] `apps/api/scripts/test-db-guard.ts:24-37`: the guard checks only the URL path and the URL port. `pg-connection-string` (2.14.1, `index.js:40-64`) copies every query parameter into the connection config, and `?host=` / `?port=` take precedence over the URL's host and port. So `postgres://labsafe:labsafe@localhost:5443/labsafe_test?port=5442` or `…?host=some.remote.host` passes the guard but connects somewhere else. The host is not checked either. Today every caller passes the hard-coded `TEST_DATABASE_URL`, so nothing can go wrong yet, but this guard is the only protection behind the E01-D4 hard rule and later epics will reuse it. Fix: also refuse any URL that has a query string or hash, and require the hostname to be `localhost` or `127.0.0.1`. Add those URLs to the TC-10.1 `REFUSED_URLS` list.
- [x] F2 [minor][be] `apps/api/src/common/error.filter.ts:45-53`: every non-`AppException` error other than a 400 or 404 `HttpException` becomes 500 `INTERNAL_ERROR` and is logged as a server error. This includes client errors that Express or Nest raise on their own, for example body-parser's `PayloadTooLargeError` (a JSON body over 100 kB on any `/api` path; Nest's `mapExternalException` passes it through unchanged), a 405, and Nest's own `ForbiddenException`, which a guard throws when it returns `false`. So an oversized request is reported as "Something went wrong." with an error log, and the deny-by-default guard that E02 adds would answer 500 instead of 403 unless E02 remembers to change the filter. The ticket asked for this behaviour, so this is a hardening note, not a broken acceptance criterion. Fix: for any `HttpException` (or any error with a numeric 4xx `status`/`statusCode`) that has no mapped code yet, answer with its real status and a generic message, and log it only at `warn`. Or write down in design §4 / `apps/api/CLAUDE.md` that E02 must map 401/403 in the filter before it adds the guard. → fixed: the error filter now keeps the real status of any 4xx (Nest HttpException or error with numeric status/statusCode, e.g. 403, 405, 413) with new shared code REQUEST_REJECTED and a generic message, logged at warn; 400/404 and 5xx unchanged.
- [ ] F3 [minor][be] `apps/api/src/modules/health/health.service.ts:14`: the empty `catch` drops the database error without logging it. When `/api/health` answers 503, the server log has nothing that explains why (wrong password, refused, timeout). Fix: log the cause with Nest's `Logger` at `warn` before throwing the `AppException`. Keep it out of the response, as TC-5.1 already checks.
- [ ] F4 [minor][be] `apps/api/src/main.ts:27`: `void bootstrap()` leaves start-up failures other than `ConfigError` unhandled. If the database is down when the API starts (for example `pnpm dev` before `pnpm db:up`), `TypeOrmModule` retries for about 30 s and then the process dies with an unhandled-rejection stack trace. That works against the "clear message, no stack trace" intent of AC7 and design §12. Fix: `bootstrap().catch(...)`, print one line (for example "Cannot reach the database at DATABASE_URL's host; run `pnpm db:up`") and `process.exit(1)`. Optionally lower `retryAttempts` in development.
- [ ] F5 [minor][docs] `docs/epics/E01-foundation/S01.1-workspace-api-quality-gate/story.md:101`: TC-10.4 (test database stopped → `pnpm test:int` prints only "run `pnpm db:up`") was never run (BE-05 implementation notes). - [ ] F6 [minor][docs] `docs/epics/E01-foundation/design.md:82`: the design no longer matches what was built, and the deviations are recorded only in ticket notes. §5 says `pnpm typecheck` is `pnpm -r typecheck`, but it now builds shared first (BE-01). §5 says `pnpm dev` loads `.env`, but it loads `../../.env`. - [ ] F8 [minor][be] `apps/api/src/common/error.filter.ts:26-28`: `clientErrorStatus` trusts the `status`/`statusCode` of *any* object, not only errors that come from the incoming request. Round 1's F2 suggested this, and the suggestion was too broad. Errors from outgoing calls also carry a numeric `status`. The clearest case is the OpenAI-compatible client for the Groq LLM provider (design doc D11): its `APIError` has `status` 401 (bad `AI_API_KEY`), 400, 404 (unknown model) or 429. If a later service lets one of these escape, the browser now gets the provider's status instead of a 500. A provider 401 would reach the web app as 401, which E02's client will likely read as "your session expired". A provider 404 becomes `NOT_FOUND` "Not found.", and a provider 400 becomes `VALIDATION_FAILED`. The log is also only a one-line `warn` with no stack, so a broken API key would look like a user mistake in the logs. Before the fix these errors fell back to a safe 500 with a full `error` log. No code in this story calls out yet, so nothing breaks today. Fix: trust a status that is not from an `HttpException` only when the error also has `expose === true` (the `http-errors` marker that body-parser and serve-static set for client errors; SDK errors don't have it). Add a unit test showing that `Object.assign(new Error('provider'), { status: 401 })` without `expose` still gives 500 `INTERNAL_ERROR` with an `error` log. Adjust the existing "statusCode only" and "non-Nest 400/404" tests to set `expose: true`.
